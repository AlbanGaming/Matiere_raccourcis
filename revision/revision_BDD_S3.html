01

Jointures (TP01)

Deux syntaxes existent pour joindre des tables — ne jamais les mélanger dans une même requête.

Ancienne syntaxe (virgules) 
SELECT ...
FROM chambre c, agent_entretien a
WHERE a.agt_id = c.agt_id
AND UPPER(a.agt_nom) IN ('BOUSSEL','FECHOL')
AND chb_communique IS NOT NULL;
Syntaxe ANSI (JOIN) 
SELECT ...
FROM chambre c
  JOIN agent_entretien a ON a.agt_id = c.agt_id
WHERE UPPER(a.agt_nom) IN ('BOUSSEL','FECHOL')
AND chb_communique IS NOT NULL;

Une jointure classique peut aussi passer par plusieurs INNER JOIN successifs (ex. client → titre → adresse → planning → chambre), ou être remplacée par des sous-requêtes corrélées avec IN :

SELECT t.tit_lib ||' '|| c.cli_nom ||' '|| c.cli_prenom
FROM client c
  JOIN titre t ON t.tit_code = c.tit_code
WHERE cli_id IN (SELECT cli_id FROM adresse WHERE UPPER(adr_ville)='REIMS')
AND cli_id IN (SELECT cli_id FROM planning WHERE pln_jour BETWEEN ...);
À retenir Jointure = combiner des tables sur une clé commune (ON). Sous-requête IN = filtrer une table par rapport à une liste issue d'une autre table. Les deux donnent souvent le même résultat mais ne sont pas interchangeables si on veut afficher des colonnes de la table filtrée.
02

Jointures externes

Une jointure externe garde les lignes d'une table même quand il n'y a pas de correspondance dans l'autre.

Syntaxe Oracle (+) 
FROM agent_entretien a, chambre c
WHERE a.agt_id = c.agt_id(+)

le (+) se met du côté de la table qui peut manquer (ici chambre) : LEFT JOIN.

Syntaxe ANSI 
FROM agent_entretien a
  LEFT JOIN chambre c ON a.agt_id = c.agt_id

agent_entretien = table maître, chambre = table esclave.

Cas typique : agents entre 50 et 60 ans même sans chambre affectée. On utilise NVL/NVL2 pour gérer l'affichage des colonnes NULL côté esclave :

SELECT DECODE(agt_sx,1,'M. ','Mme ')||agt_prenom||' '||agt_nom "Agent",
       NVL2(chb_numero, 'N°'||chb_numero, 'AUCUNE CHAMBRE') "Chambre",
       NVL(chb_etage,'--') "Etage"
FROM agent_entretien a
  LEFT JOIN chambre c ON a.agt_id = c.agt_id
WHERE TRUNC(MONTHS_BETWEEN(SYSDATE,a.agt_dnais)/12) BETWEEN 50 AND 60;
Clients / agents "orphelins" Pour trouver ce qui n'a aucune correspondance (clients sans réservation, agents sans chambre) : jointure externe + IS NULL sur la clé de la table esclave. 
FROM agent_entretien a
  LEFT JOIN chambre c ON a.agt_id = c.agt_id
WHERE c.agt_id IS NULL   -- pas chb_numero au hasard : la clé de jointure
03

Priorité des conditions — le piège central

C'est le point que la prof souligne explicitement : où placer une condition qui porte sur la table esclave d'une jointure externe.

Le piège Si la condition sur la table esclave est mise dans le WHERE, elle s'applique après la jointure externe : les lignes où la table esclave était NULL (justement ce qu'on voulait garder) se retrouvent éliminées. Résultat : on perd l'effet du LEFT JOIN, la requête se comporte comme un INNER JOIN.
Faux (perd les lignes sans FAX) 
FROM client c
  LEFT JOIN telephone t ON c.cli_id=t.cli_id
WHERE t.typ_code = 'FAX'
Correct — condition dans le ON 
FROM client c
  LEFT JOIN telephone t
    ON c.cli_id = t.cli_id AND t.typ_code = 'FAX'

Même logique pour une condition de date sur la table esclave (planning) :

-- Correct : toutes les chambres, réservées ou non, ce jour-là
FROM chambre c
  LEFT JOIN planning p
    ON c.chb_id = p.chb_id
    AND pln_jour = TO_DATE('26/12/2007','DD/MM/YYYY')
Règle générale Condition sur la table maître → dans le WHERE (filtre normal).
Condition sur la table esclave d'une jointure externe → dans le ON, sinon elle annule l'effet du LEFT/RIGHT JOIN.

Avec l'ancienne syntaxe (+), ce piège n'existe pas de la même façon : la condition peut rester dans le WHERE tant qu'elle porte sur une sous-requête déjà filtrée en amont (cf. exemples avec sous-requête dans le FROM).

04

Regroupement

GROUP BY résume des lignes ; HAVING filtre des groupes (jamais des lignes individuelles).

SELECT e.cli_id, cli_nom||' '||cli_prenom AS CLIENT,
       COUNT(EML_ID)||' emails' AS "PLUSIEURS ADR"
FROM CLIENT c JOIN EMAIL e ON c.cli_id=e.cli_id
GROUP BY e.cli_id, cli_nom, cli_prenom
HAVING COUNT(EML_ID) > 1;
Le mieux du meilleur Pour "le max par groupe" (ex. chambre avec le plus de couchages par étage) : sous-requête corrélée comparant chaque ligne au MAX() de son propre groupe. 
WHERE chb_couchage = (SELECT MAX(cm.chb_couchage)
                       FROM chambre cm
                       WHERE cm.chb_etage = c.chb_etage)

Combiner GROUP BY avec une jointure externe : la condition sur la table esclave va toujours dans le ON, même quand on compte ensuite avec COUNT().

FROM agent_entretien a
  LEFT JOIN chambre c ON (c.agt_id=a.agt_id AND chb_couchage > 2)
WHERE agt_sx = 2
GROUP BY agt_nom;   -- COUNT(chb_id) vaut 0 si aucune ligne rattachée

HAVING COUNT(x) = (SELECT MAX(COUNT(y)) FROM ... GROUP BY ...) est le patron classique pour "le client qui a le plus de X" — sous-requête qui refait le même GROUP BY pour calculer le maximum.

05

CTE — Common Table Expression

Le WITH nomme une sous-requête réutilisable, plus lisible qu'une sous-requête imbriquée dans le FROM.

WITH agt_actifs AS (
  SELECT DISTINCT agt_nom, agt_prenom, agt_emb
  FROM agent_entretien a
    INNER JOIN chambre c ON a.agt_id = c.agt_id
  ORDER BY agt_emb
)
SELECT agt_nom||' '||agt_prenom AGENT, EXTRACT(YEAR FROM agt_emb) embauche
FROM agt_actifs
WHERE rownum <= 2;
Où elle remplace quoi Une CTE remplace typiquement une sous-requête placée après le FROM (ex. (SELECT cli_id, tel_numero FROM telephone WHERE typ_code='FAX') t) : on la déclare une fois en haut avec WITH, puis on la joint comme une table normale — souvent en LEFT JOIN si elle joue le rôle de table esclave. 
WITH planning_noel AS (
  SELECT cli_id, pln_jour, chb_id FROM planning
  WHERE pln_jour = TO_DATE('26/12/2007','DD/MM/YYYY')
)
SELECT chb_numero, cli_id
FROM chambre c LEFT JOIN planning_noel p ON c.chb_id = p.chb_id
ORDER BY 1;

La condition de filtrage (date, type) est faite à l'intérieur de la CTE — donc le piège de priorité du point 3 ne se pose plus une fois la CTE jointe en LEFT JOIN simple sur la clé.

06

Pièges liés à NULL

NOT IN + NULL = danger Si la colonne testée par NOT IN (sous-requête) peut contenir NULL, la sous-requête entière renvoie un résultat indéterminé et zéro ligne n'est retournée — même si intuitivement des lignes devraient matcher.
Risqué si agt_id peut être NULL dans chambre 
WHERE agt_id NOT IN (SELECT agt_id FROM chambre)
Sûr : NOT EXISTS ou filtrer les NULL 
WHERE NOT EXISTS (SELECT NULL FROM chambre c
                   WHERE a.agt_id = c.agt_id)

NOT EXISTS est la méthode la plus fiable et la plus performante pour "n'a jamais / n'a aucun" — à privilégier par réflexe dès que la colonne de la sous-requête n'est pas garantie NON NULL.

Fonctions utiles pour NULL NVL(col, valeur_defaut) — remplace NULL par une valeur.
NVL2(col, si_non_null, si_null) — teste la présence avant de choisir quoi afficher.
col IS NULL / IS NOT NULL — jamais = NULL.

Repère rapide : si l'énoncé garantit "colonne obligatoire" (NOT NULL) dans la table de la sous-requête, NOT IN est safe. Sinon, réflexe NOT EXISTS.

✓

Checklist avant l'examen

  • Je ne mélange jamais virgules et JOIN dans une même requête.
  • Je sais repérer la table maître / table esclave d'un LEFT ou RIGHT JOIN.
  • Condition sur la table esclave → dans le ON, jamais dans le WHERE (sinon ça annule le LEFT JOIN).
  • "N'a jamais / aucun" → LEFT JOIN + IS NULL sur la clé, ou NOT EXISTS.
  • NOT IN est dangereux si la colonne peut être NULL → je préfère NOT EXISTS.
  • HAVING filtre des groupes, WHERE filtre des lignes avant regroupement.
  • Une CTE (WITH ... AS) remplace une sous-requête du FROM pour plus de lisibilité.
  • NVL / NVL2 pour afficher proprement les colonnes NULL issues d'une jointure externe.
