01

Contraintes d'intégrité

Une contrainte est une règle déclarée dans la table : Oracle la vérifie à chaque INSERT / UPDATE / DELETE, sans code à écrire.

ContrainteRôleExemple (TP03)
PRIMARY KEYUnique + non NULL. Une seule par table. Crée un index automatiquement.CONSTRAINT pk_agt PRIMARY KEY
FOREIGN KEY / REFERENCESLa valeur doit exister dans la table référencée (ou être NULL).REFERENCES agent_entretien(agt_id)

Contrainte de colonne ou contrainte de table

De colonne : écrite juste après la colonne 
chb_id INTEGER
  CONSTRAINT pk_chambre PRIMARY KEY,
agt_id CHAR(3)
  CONSTRAINT fk_agt_id
  REFERENCES agent_entretien(agt_id),
cli_id INTEGER NOT NULL
  CONSTRAINT fk_tel_client
  REFERENCES client(cli_id),
De table : après toutes les colonnes 
CONSTRAINT pk_planning
  PRIMARY KEY (chb_id, pln_jour),
CONSTRAINT fk_facture_adresse
  FOREIGN KEY (cli_id, adr_id)
  REFERENCES adresse(cli_id, adr_id),
CONSTRAINT pk_dates
  CHECK (fac_date <= fac_dat_pmt)
La règle Dès qu'une contrainte porte sur 2 colonnes ou plus (clé primaire composée, clé étrangère composée, CHECK qui compare deux colonnes), elle s'écrit en contrainte de table. Tout le reste peut s'écrire en contrainte de colonne.
  • NOT NULL ne s'écrit qu'en contrainte de colonne.
  • En contrainte de colonne, une clé étrangère s'écrit avec REFERENCES seul ; en contrainte de table il faut FOREIGN KEY (col) REFERENCES ….
  • Une colonne peut porter plusieurs contraintes de colonne (ex. NOT NULL + REFERENCES sur cli_id de TELEPHONE).
  • CONSTRAINT nom est facultatif : sans nom, Oracle génère SYS_C00xxxx. Nommer aide à lire les erreurs et à faire un DROP CONSTRAINT.

Les erreurs corrigées dans le script de création

Ordre de création
  • Une table référencée doit exister avant la table qui la référence : TYPE avant TELEPHONE, CLIENT avant EMAIL.
  • Une clé étrangère doit pointer vers une clé primaire ou UNIQUE. TITRE sans clé primaire faisait échouer la création de CLIENT.
  • À la suppression, c'est l'inverse : les tables filles d'abord, ou DROP TABLE … CASCADE CONSTRAINTS qui supprime aussi les FK qui pointent vers la table.
  • "TYPE" entre guillemets : TYPE est un mot réservé.

Clé étrangère réflexive : une chambre communique avec une autre chambre de la même table.

chb_communique INTEGER CONSTRAINT fk_chambre REFERENCES chambre(chb_id)

CHECK : ce qu'il peut faire et ce qu'il ne peut pas

CHECK (chb_numero != 13)
CHECK (chb_bain IN (0,1))
CHECK (SUBSTR(chb_poste_tel,1,1) BETWEEN '0' AND '9')
CHECK (eml_adresse LIKE '%@%.%')
CHECK (agt_sx IN ('1','2'))
Pièges CHECK
  • Un CHECK n'est violé que si la condition est FAUSSE. Si elle vaut NULL (inconnu), la ligne passe : fac_dat_pmt NULL est accepté par fac_date <= fac_dat_pmt.
  • Un CHECK ne lit que la ligne en cours : pas d'autre table, pas d'autre ligne, pas de sous-requête.
  • Un CHECK n'accepte pas SYSDATE (fonction non déterministe). « Date de réservation ≥ aujourd'hui » demande donc un trigger.

Erreurs à reconnaître

ORA-00001clé primaire / UNIQUE violée (doublon) ORA-01400insertion de NULL dans une colonne NOT NULL ORA-02290contrainte CHECK violée ORA-02291clé parent introuvable (on insère un fils sans père) ORA-02292enregistrement fils existant (on supprime un père qui a des fils)
02

Remplir et modifier les tables

INSERT … SELECT depuis un autre schéma

INSERT INTO titre SELECT * FROM hotel.titre;

-- colonnes dans un ordre différent : on les liste dans l'ordre de la table cible
INSERT INTO chambre
  SELECT chb_id, chb_communique, agt_id, chb_numero, chb_etage,
         chb_bain, chb_douche, chb_wc, chb_poste_tel, chb_couchage
  FROM hotel.chambre;

-- pas le même nombre de colonnes + filtre sur 2007
INSERT INTO planning
  SELECT chb_id, pln_jour, cli_id, nb_pers FROM hotel.planning
  WHERE EXTRACT(YEAR FROM pln_jour) = 2007;
À retenir
  • On insère dans l'ordre de l'intégrité référentielle : les pères (TITRE, CLIENT, TYPE…) avant les fils (TELEPHONE, ADRESSE…).
  • SELECT * ne marche que si les deux tables ont les mêmes colonnes, dans le même ordre.
  • Pour accéder à la table d'un autre utilisateur : schema.table (hotel.client), à condition d'avoir le privilège.

CREATE TABLE … AS SELECT

CREATE TABLE tarif AS
  (SELECT * FROM hotel.tarif WHERE EXTRACT(YEAR FROM trf_date_debut) = 2007);
ALTER TABLE tarif ADD CONSTRAINT pk_tarif PRIMARY KEY (trf_date_debut);

-- copie vide d'une table : condition toujours fausse
CREATE TABLE old_fact AS (SELECT * FROM facture WHERE fac_id IS NULL);
Piège Un CREATE TABLE AS SELECT copie la structure (colonnes, types) et les données, et seulement les contraintes NOT NULL. Clé primaire, clés étrangères et CHECK ne sont pas copiées : il faut les rajouter avec ALTER TABLE.

ALTER TABLE

ALTER TABLE telephone
  ADD CONSTRAINT chk_localisation
      CHECK (tel_localisation IN ('domicile','portable','bureau'))
  MODIFY tel_localisation DEFAULT 'domicile';

ALTER TABLE facture ADD total NUMBER;              -- nouvelle colonne
ALTER TABLE telephone DROP CONSTRAINT fk_tel_client;
DEFAULT et NULL
  • La valeur par défaut n'est utilisée que si la colonne est absente de l'INSERT : INSERT INTO telephone (tel_id, cli_id, typ_code, tel_numero) VALUES (…) → 'domicile'.
  • Si on écrit NULL explicitement dans le VALUES, la colonne vaut NULL, pas la valeur par défaut.
  • Ajouter une contrainte à une table remplie échoue si des lignes existantes ne la respectent pas.

ON DELETE CASCADE

Supprimer DUPONT Alain échoue (ORA-02292) tant qu'il a des téléphones. On ne peut pas modifier une contrainte existante : on la supprime puis on la recrée.

ALTER TABLE telephone DROP CONSTRAINT fk_tel_client;
ALTER TABLE telephone ADD CONSTRAINT fk_tel_client
  FOREIGN KEY (cli_id) REFERENCES client(cli_id) ON DELETE CASCADE;
-- idem pour EMAIL, ADRESSE, PLANNING (toutes les filles de CLIENT)
Options d'une clé étrangère
  • Sans option : on ne peut pas supprimer un père qui a des fils.
  • ON DELETE CASCADE : supprimer le père supprime ses fils.
  • ON DELETE SET NULL : les fils restent, leur clé étrangère passe à NULL.
  • Oracle n'a pas de ON UPDATE CASCADE.
  • La cascade s'enchaîne : supprimer un client supprime ses adresses, ce qui bloque si une FACTURE référence ces adresses sans cascade.
03

Privilèges, vues et rôles

GRANT privilèges ON table TO utilisateur | rôle | PUBLIC [WITH GRANT OPTION];
REVOKE privilèges ON table FROM utilisateur | rôle | PUBLIC;

Privilèges objet : SELECT, INSERT, UPDATE, DELETE, ALTER, INDEX, REFERENCES, ou ALL [PRIVILEGES]. Le propriétaire de la table a tous les droits dessus et peut les donner.

GRANT SELECT ON client TO PUBLIC;                         -- tout le monde
GRANT SELECT, INSERT, DELETE, UPDATE(nb_pers) ON planning TO tests2;
GRANT UPDATE(tit_code, cli_nom, cli_prenom, cli_enseigne) ON client TO tests2;
GRANT SELECT ON client TO tests2 WITH GRANT OPTION;       -- peut redistribuer
REVOKE ALL PRIVILEGES ON client FROM PUBLIC, tests2;

-- côté voisin : préfixer par le propriétaire
SELECT cli_nom, adr_ville
FROM tests3.client c JOIN tests3.adresse a ON a.cli_id = c.cli_id;
Restreindre colonnes et lignes UPDATE, INSERT et REFERENCES acceptent une liste de colonnes. SELECT non : pour cacher une colonne (le salaire) ou des lignes (agents partis), on passe par une vue et on donne le droit sur la vue. 
CREATE OR REPLACE VIEW agt_vue AS
  (SELECT agt_id, agt_nom, agt_prenom, agt_sx, agt_dnais, agt_emb, agt_dpt
   FROM agent_entretien
   WHERE agt_dpt IS NULL);
GRANT SELECT ON agt_vue TO tests2;
Pièges REVOKE
  • Si le droit a été donné à PUBLIC et à tests2, REVOKE … FROM tests2 ne l'empêche pas de lire : il garde le droit via PUBLIC.
  • Un droit reçu WITH GRANT OPTION puis redistribué : quand on le retire au premier, ceux à qui il l'a donné le perdent aussi (révocation en cascade).

Rôles

Un rôle regroupe des privilèges qu'on attribue en une fois à plusieurs utilisateurs.

CREATE ROLE ro_hotel_tests3;
GRANT UPDATE(agt_id) ON chambre TO ro_hotel_tests3;
GRANT SELECT, UPDATE, INSERT, DELETE ON tarif    TO ro_hotel_tests3;
GRANT SELECT, UPDATE, INSERT, DELETE ON planning TO ro_hotel_tests3;
GRANT ro_hotel_tests3 TO sandron, estelle;     -- on donne le rôle aux personnes
DROP ROLE ro_hotel_tests3;                     -- tous perdent les droits du rôle

Ordre : créer le rôle → lui donner les privilèges → donner le rôle aux utilisateurs. Un rôle reçu devient actif à la connexion suivante de l'utilisateur.

04

Triggers LMD : syntaxe et fonctionnement

CREATE [OR REPLACE] TRIGGER nom
{BEFORE | AFTER} {INSERT | UPDATE [OF col] | DELETE} [OR …]
ON table
[FOR EACH ROW [WHEN (condition)]]     -- présent = trigger ligne, absent = trigger d'état
[DECLARE
   variables ;]
BEGIN
   instructions ;
END;
/

Trigger d'état (par ordre) ou trigger ligne

Trigger d'étatTrigger ligne
Écrituresans FOR EACH ROWavec FOR EACH ROW
Exécutions1 fois par ordre SQL, même si 0 ligne est touchée1 fois par ligne touchée (0 si aucune)
:NEW / :OLDinterdits (erreur de compilation)disponibles
Usage typeautoriser / refuser l'ordre entier (jour, heure, utilisateur)contrôler ou modifier chaque ligne, mettre à jour une autre table

Ce qui les différencie, c'est uniquement la directive FOR EACH ROW : les deux peuvent être BEFORE ou AFTER, sur INSERT, UPDATE ou DELETE.

Ordre de déclenchement

Pour un ordre qui touche plusieurs lignes : BEFORE état → pour chaque ligne (BEFORE ligne → modification + vérification des contraintes → AFTER ligne) → AFTER état.

Outils dans le corps du trigger

IF INSERTING THEN …  ELSIF UPDATING THEN …  ELSIF DELETING THEN … END IF;

RAISE_APPLICATION_ERROR(-20120, 'Désolé pas de modifs aujourd''hui !');

SELECT chb_couchage INTO nbc FROM chambre WHERE chb_id = :NEW.chb_id;

DBMS_OUTPUT.PUT_LINE('Résa effectuée');   -- visible après SET SERVEROUTPUT ON
RAISE_APPLICATION_ERROR Code entre -20000 et -20999. L'erreur annule l'ordre SQL entier qui a déclenché le trigger : si elle survient sur la 3e ligne d'un UPDATE de 5 lignes, aucune des 5 n'est modifiée. Les ordres précédents de la transaction ne sont pas annulés.
Pièges
  • SELECT … INTO doit ramener exactement une ligne : 0 ligne → NO_DATA_FOUND, plusieurs → TOO_MANY_ROWS. D'où le WHERE chb_id = :NEW.chb_id.
  • Pas de COMMIT ni de ROLLBACK dans un trigger LMD : il compile, mais échoue à l'exécution (ORA-04092).
  • Un trigger créé « avec erreurs de compilation » est invalide : tout INSERT/UPDATE/DELETE sur la table échoue ensuite (ORA-04098) tant qu'il n'est pas corrigé ou désactivé.
  • Dans la clause WHEN, on écrit NEW.col sans les deux-points ; dans le corps, :NEW.col.

Gérer un trigger

ALTER TRIGGER jourok DISABLE;            -- ENABLE pour réactiver
ALTER TABLE agent_entretien DISABLE ALL TRIGGERS;
DROP TRIGGER jourok;
SHOW ERRORS                              -- détail des erreurs de compilation

:NEW et :OLD

Ordre:OLD:NEW
INSERTNULL (pas d'ancienne ligne)valeurs insérées
UPDATEvaleurs avantvaleurs après
DELETEvaleurs suppriméesNULL (pas de nouvelle ligne)

Vrai en BEFORE comme en AFTER : en INSERT, :OLD est toujours NULL ; en DELETE, :NEW est toujours NULL.

ActionBEFORE ligneAFTER ligneTrigger d'état
Lire :NEW / :OLDouiouinon (compilation)
Modifier :NEW.col := …ouinon (compilation)non
Modifier :OLDjamaisjamaisnon
Le réflexe Pour changer une valeur de la ligne qu'on insère ou modifie, on affecte :NEW dans un trigger BEFORE … FOR EACH ROW. On ne fait jamais d'UPDATE sur la table du trigger. 
:NEW.pln_jour := TRUNC(SYSDATE);
:NEW.num_clt  := v_nb;
:NEW.remise_mnt := NVL(:NEW.mnt * :NEW.qte * :NEW.remise_pourcent / 100, 0);
Tester la ligne insérée En BEFORE INSERT, la ligne n'est pas encore dans la table : pour savoir si le client inséré est de Reims, on teste :NEW.ville_clt = 'REIMS', pas un SELECT … FROM client (sans WHERE il ramène toutes les lignes) et pas :OLD (NULL en INSERT).
06

Trigger ou contrainte ?

Si une contrainte déclarative suffit, on la préfère : plus simple, plus rapide, impossible à oublier. Le trigger sert quand la règle dépasse la ligne en cours.

RègleSolution
sexe ∈ {1, 2} ; étage ∈ {RDC, 1er, 2e}CHECK
date d'arrivée < date de départ (même ligne)CHECK de table
le NumPat d'un séjour existe dans PATIENTFOREIGN KEY
supprimer un patient supprime ses séjoursFK ON DELETE CASCADE
date d'intervention entre l'arrivée et le départ du séjourTrigger (autre table)
nb de personnes ≤ couchages de la chambreTrigger (autre table)
date de réservation ≥ aujourd'huiTrigger (SYSDATE interdit dans un CHECK)
pas de modification le samediTrigger d'état
tenir à jour le TOTAL d'une factureTrigger sur LIGNE_FACTURE
archiver les factures suppriméesTrigger BEFORE DELETE

Supprimer les lignes de facture avec la facture : le trigger du TP04 marche, mais la clé étrangère ON DELETE CASCADE est la meilleure solution.

07

Tables mutantes et trigger composé

ORA-04091 : table en mutation Un trigger ligne ne peut pas lire ni modifier la table sur laquelle il est posé. Il compile, mais l'erreur arrive à l'exécution. Exemple : contrôler le nouveau salaire par rapport à AVG(agt_salaire) de AGENT_ENTRETIEN dans un trigger BEFORE UPDATE … FOR EACH ROW sur AGENT_ENTRETIEN.
  • Les triggers d'état ne sont pas concernés : ils peuvent interroger leur table.
  • Lire ou modifier une autre table dans un trigger ligne est permis (CHAMBRE depuis PLANNING, FACTURE depuis LIGNE_FACTURE).
  • Cas toléré par Oracle : un INSERT … VALUES d'une seule ligne avec un trigger BEFORE INSERT ligne qui lit sa table (ex. SELECT MAX(num_clt)+1). Avec un INSERT … SELECT, l'erreur revient.

La solution : le trigger composé

Une seule unité avec des variables partagées et 4 sections. On fait la requête sur la table dans la partie état, puis on contrôle chaque ligne.

CREATE OR REPLACE TRIGGER mut_comp_trigger
FOR UPDATE ON agent_entretien
COMPOUND TRIGGER
  g_avg_salaire INTEGER;                 -- partagé entre les sections

  BEFORE STATEMENT IS
  BEGIN
    SELECT ROUND(AVG(agt_salaire)) INTO g_avg_salaire FROM agent_entretien;
  END BEFORE STATEMENT;

  AFTER EACH ROW IS
  BEGIN
    IF :NEW.agt_salaire <= g_avg_salaire THEN
      RAISE_APPLICATION_ERROR(-20001, 'Salaire inférieur à la moyenne');
    END IF;
  END AFTER EACH ROW;

  AFTER STATEMENT IS
  BEGIN
    DBMS_OUTPUT.PUT_LINE('Fin de la mise à jour');
  END AFTER STATEMENT;
END mut_comp_trigger;
/

Sections possibles : BEFORE STATEMENT, BEFORE EACH ROW, AFTER EACH ROW, AFTER STATEMENT. On écrit FOR UPDATE ON table COMPOUND TRIGGER, sans BEFORE/AFTER en tête.

08

TP04 pas à pas

Exo 1 : trigger d'état, pas de modification le samedi

CREATE OR REPLACE TRIGGER jourok
BEFORE DELETE OR UPDATE OR INSERT ON agent_entretien
BEGIN
  IF TO_CHAR(SYSDATE,'fmDAY') = 'SAMEDI' THEN
    RAISE_APPLICATION_ERROR(-20120, 'Désolé pas de modifs de la table aujourd''hui !');
  END IF;
END;
/

Pas de FOR EACH ROW : la décision porte sur l'ordre entier. fm retire les espaces de remplissage de DAY (sinon 'SAMEDI '). Le nom du jour dépend de la langue de la session. Pour le désactiver : ALTER TRIGGER jourok DISABLE, avec le nom du trigger.

Exo 2 : archiver une facture et ses lignes avant suppression

CREATE OR REPLACE TRIGGER tr_facture
BEFORE DELETE ON facture
FOR EACH ROW
BEGIN
  INSERT INTO old_fact VALUES (:OLD.fac_id, :OLD.pmt_code, :OLD.cli_id,
                               :OLD.adr_id, :OLD.fac_date, :OLD.fac_dat_pmt);
  INSERT INTO old_lg (SELECT * FROM ligne_facture WHERE fac_id = :OLD.fac_id);
  DELETE FROM ligne_facture WHERE fac_id = :OLD.fac_id;
END;
/

En DELETE on n'a que :OLD. BEFORE : les lignes filles sont supprimées avant que la suppression de la facture vérifie la clé étrangère, sinon ORA-02292. Un ROLLBACK (hors trigger) annule tout.

Exo 3 : corriger la date et contrôler la capacité

CREATE OR REPLACE TRIGGER tr_planning
BEFORE INSERT OR UPDATE ON planning
FOR EACH ROW
DECLARE
  nbc INTEGER;
BEGIN
  IF :NEW.pln_jour < SYSDATE OR :NEW.pln_jour IS NULL THEN
    :NEW.pln_jour := TRUNC(SYSDATE);        -- modifier :NEW → BEFORE obligatoire
  END IF;
  SELECT chb_couchage INTO nbc FROM chambre WHERE chb_id = :NEW.chb_id;
  IF :NEW.nb_pers > nbc THEN
    RAISE_APPLICATION_ERROR(-20222, 'Pas assez de place dans cette chambre !');
  END IF;
END;
/

Le trigger remplace une date passée ou NULL : un NOT NULL sur pln_jour n'empêche pas l'insertion de NULL ici, car le BEFORE corrige la valeur avant la vérification des contraintes. Lire CHAMBRE est permis (autre table).

Exo 4 : maintenir le total de la facture

CREATE OR REPLACE TRIGGER tr_total_facture
BEFORE INSERT OR UPDATE OR DELETE ON ligne_facture
FOR EACH ROW
DECLARE
  new_mnt facture.total%TYPE;
  old_mnt facture.total%TYPE;
BEGIN
  old_mnt := (:OLD.mnt*:OLD.qte - :OLD.remise_mnt) * (1 + :OLD.taux_tva/100);
  IF DELETING THEN
    UPDATE facture SET total = ROUND(total - old_mnt, 2) WHERE fac_id = :OLD.fac_id;
  ELSE
    :NEW.remise_mnt := NVL(:NEW.mnt*:NEW.qte*:NEW.remise_pourcent/100, 0);
    new_mnt := (:NEW.mnt*:NEW.qte - :NEW.remise_mnt) * (1 + :NEW.taux_tva/100);
    IF INSERTING THEN
      UPDATE facture SET total = ROUND(total + new_mnt, 2) WHERE fac_id = :NEW.fac_id;
    ELSE
      UPDATE facture SET total = ROUND(total - old_mnt + new_mnt, 2) WHERE fac_id = :NEW.fac_id;
    END IF;
  END IF;
END;
/

Un seul trigger pour les 3 ordres, aiguillé par INSERTING / UPDATING / DELETING. INSERT → ajoute :NEW ; DELETE → retire :OLD ; UPDATE → retire :OLD et ajoute :NEW. %TYPE reprend le type d'une colonne. UPDATE sur FACTURE autorisé (autre table).

Exo 5 : mutation puis trigger composé

Le trigger ligne qui calcule AVG(agt_salaire) sur AGENT_ENTRETIEN compile mais lève ORA-04091 à l'UPDATE. On le désactive et on le remplace par le trigger composé de la section 7.

Checklist

Rappels du QCM 1 : jointures, NULL, GROUP BY, CTE
Jointures On ne mélange pas FROM t1, t2 WHERE … et JOIN … ON dans une même requête. Une sous-requête IN filtre une table sans pouvoir afficher les colonnes de l'autre.
Jointure externe (+) du côté de la table qui peut manquer : a.agt_id = c.agt_id(+) ≡ agent_entretien a LEFT JOIN chambre c. « Ceux qui n'ont aucun… » : LEFT JOIN + IS NULL sur la clé de la table esclave.
Faux : perd les clients sans FAX 
FROM client c
  LEFT JOIN telephone t ON c.cli_id=t.cli_id
WHERE t.typ_code = 'FAX'
Juste : condition dans le ON 
FROM client c
  LEFT JOIN telephone t
    ON c.cli_id = t.cli_id AND t.typ_code = 'FAX'

Condition sur la table maître → WHERE. Condition sur la table esclave d'une jointure externe → ON (ou filtrée avant dans une sous-requête du FROM / une CTE).

GROUP BY / HAVING Toute colonne du SELECT hors agrégat va dans le GROUP BY ; pas d'alias dans le GROUP BY. WHERE filtre les lignes avant regroupement, HAVING filtre les groupes. COUNT(col) ignore les NULL, COUNT(*) non.
CTE et ROWNUM 
WITH agt_actifs AS (
  SELECT DISTINCT agt_nom, agt_emb FROM agent_entretien a
  JOIN chambre c ON a.agt_id = c.agt_id ORDER BY agt_emb)
SELECT agt_nom FROM agt_actifs WHERE ROWNUM <= 2;
ROWNUM est attribué avant le ORDER BY : on trie dans la CTE ou la sous-requête, puis on filtre.
NULL NOT IN (sous-requête) qui contient un NULL ne renvoie aucune ligne → NOT EXISTS. Tester avec IS NULL, jamais = NULL. NVL(x, y) : x et y du même type.
