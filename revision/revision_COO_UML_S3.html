Vue d'ensemble

Du besoin au code

On ne code pas une application directement. On comprend d'abord le besoin (analyse), on imagine une solution (conception), on la décrit en UML (modélisation), puis on la code (implémentation). La vérification compare le résultat au besoin de départ, et le cycle peut recommencer.

Les grandes étapes de l'analyse et conception objet

  1. Définir les besoins Vue fonctionnelle
    Cas d'utilisation, scénarios, diagrammes de séquence système.
  2. Définir le modèle du domaine Vue statique
    Les concepts du métier (Client, Séance, Réservation…), leurs attributs et leurs associations.
  3. Affecter les responsabilités Vue dynamique
    Diagrammes de séquence : quel objet fait quoi, qui appelle qui.
  4. Réaliser le diagramme de classes de conception Vue statique
    On repart du modèle du domaine et on ajoute les opérations trouvées à l'étape 3, l'héritage, le polymorphisme, les types.

Architecture en couches

Pour concevoir, on sépare l'application en couches qui ont chacune un rôle. L'interface ne contient pas de règles métier, et le métier ne sait pas comment il est affiché.

Trois vues sur un même système

UML propose plusieurs diagrammes. Chacun répond à une question différente sur le même système.

Fonctionnelle

Que veut l'utilisateur ?

  • Diagramme de cas d'utilisation
  • Scénarios
  • Diagramme de séquence système

Statique

Quelle structure pour le logiciel ?

  • Diagramme de classes
  • Diagramme d'objets

Dynamique

Quel comportement pour le logiciel ?

  • Diagrammes d'interaction : séquence (et communication)

Les vues s'enchaînent : les cas d'utilisation font apparaître les concepts du modèle du domaine (vue statique) ; les diagrammes de séquence répartissent le travail entre les objets (vue dynamique) ; on en déduit le diagramme de classes de conception, avec ses opérations, son héritage et son polymorphisme.

Modélisation fonctionnelle

Diagramme de cas d'utilisation (DUC)

Le DUC montre ce que le système doit faire pour ses utilisateurs, sans dire comment. On le fait au tout début, pendant l'analyse, souvent avec le client. Il répond à quatre questions : qui sont les utilisateurs ? que veulent-ils faire ? où s'arrête le système ? à quoi sert-il ?

  1. Système étudié : rectangle portant son nom. Ce qui est dedans est à réaliser ; ce qui est dehors ne l'est pas.
  2. Acteur : un rôle joué par quelqu'un ou quelque chose d'extérieur qui interagit avec le système. Une même personne peut jouer plusieurs rôles (un gérant qui réserve est un Client à ce moment-là).
  3. Acteur système : un autre logiciel ou matériel externe. On le dessine en bonhomme ou en rectangle avec le stéréotype «actor». Un stéréotype (texte entre « ») précise la nature d'un élément.
  4. Cas d'utilisation : ellipse. Un service rendu qui a un résultat pour l'acteur. Nom = verbe à l'infinitif + complément, vu du côté de l'acteur : « Réserver des places », pas « Gestion des réservations ».
  5. Association : trait plein entre un acteur et un cas : l'acteur participe à ce cas.

Acteur primaire ou secondaire

  • Primaire : il déclenche le cas pour obtenir un résultat (Client, Gérant). On le place par convention à gauche.
  • Secondaire : le système le sollicite pendant le cas (la Banque qui valide le paiement). On le place par convention à droite.

Un acteur peut aussi être humain ou système : ce sont deux critères différents. La banque est un acteur système secondaire.

À retenir

Le DUC n'a pas d'ordre de lecture : il ne montre ni chronologie ni flux de données. Un trait entre un acteur et un cas ne dit pas qui parle en premier. L'ordre des actions se décrit dans les scénarios.

Relations dans un DUC

Généralisation d'acteurs

Un acteur enfant hérite de tous les cas de son parent. Triangle vide pointé vers le parent.

Généralisation de cas d'utilisation

Inclusion «include»

Le cas de base exécute toujours le cas inclus ; il n'est pas complet sans lui. Sert à factoriser un comportement commun à plusieurs cas (s'identifier, par exemple).

Extension «extend»

Le cas d'extension ajoute un comportement optionnel, déclenché sous condition, à un endroit précis du cas de base : le point d'extension. Le cas de base reste complet sans l'extension.

«include»«extend»
ExécutionToujoursSeulement si la condition est vraie
Sens de la flècheCas de base → cas inclusExtension → cas de base
Le cas de base est complet seul ?NonOui
Indices dans un énoncé« doit », « obligatoirement », « à chaque fois »« peut », « éventuellement », « si… »
Moyen mnémotechnique

La flèche part toujours du cas qui dépend de l'autre pour être décrit. Le cas de base dépend du cas qu'il inclut ; l'extension dépend du cas de base qu'elle complète.

Piège. N'abusez pas de ces relations. Un DUC sert à discuter des besoins, pas à découper le programme en fonctions. Martin Fowler (UML Distilled) : le grand danger des cas d'utilisation est de les rendre trop compliqués ; on se fait généralement moins de mal en en faisant trop peu qu'en en faisant trop.

Exercice : de l'énoncé au DUC

Sur le site du cinéma :

  • Pour réserver des places, le client doit être identifié par le système.
  • Lors d'une réservation, le client peut utiliser sa carte fidélité pour obtenir une réduction.
  • À la fin de la réservation, le client paie ; le paiement est validé par la banque.

Dessinez le DUC, puis comparez.

Voir la correction
  • « doit être identifié » : obligatoire à chaque réservation → «include» de Réserver vers S'identifier.
  • « peut utiliser » : optionnel → «extend» de Utiliser sa carte fidélité vers Réserver.
  • « à la fin, le client paie » : toujours exécuté → «include» de Réserver vers Payer. L'ordre (« à la fin ») ne se dessine pas : il ira dans le scénario.
  • La banque est un acteur secondaire (système), reliée au cas Payer.

Marche à suivre

  1. Délimiter le système : ce qui est à réaliser et ce qui reste dehors.
  2. Lister les acteurs, en précisant pour chacun : humain ou système, primaire ou secondaire.
  3. Pour chaque acteur primaire, lister ses objectifs : un objectif = un cas d'utilisation.
  4. Relier acteurs et cas, puis ajouter héritage, «include» et «extend» seulement s'ils clarifient.
  5. Regrouper les cas en paquetages si le système est gros.
  6. Pour les cas les plus complexes : rédiger les scénarios, puis le diagramme de séquence système.

Scénarios

Un scénario est une petite histoire : une succession particulière d'actions et d'interactions entre les acteurs et le système. Un cas d'utilisation = une collection de scénarios.

TypeCe qui se passeObjectif atteint ?
NominalLe déroulement normal, quand tout se passe bien.Oui
AlternatifUne variante qui s'écarte du nominal à un point d'entrée, puis le rejoint (reprise).Oui
Exception (erreur)Un problème empêche de continuer ; le cas se termine.Non

Ce que contient un scénario

  • Nom du scénario.
  • Pré-conditions : ce qui doit être vrai avant de commencer.
  • Histoire : les étapes numérotées, en version textuelle (phrases) ou tabulaire (tableau acteur / système).
  • Post-conditions : ce qui est vrai à la fin.
  • Pour un alternatif : le point d'entrée (étape où l'on diverge) et la reprise (étape où l'on revient dans le nominal).
  • Pour une exception : le point d'entrée et la mention cas terminé.

Nominal : Réserver des places

Pré-conditions : le client est identifié ; la séance est programmée.

Version textuelle : le client recherche un film. Le système affiche les séances. Le client choisit une séance et un nombre de places. Le système vérifie les places disponibles et affiche le récapitulatif avec le prix. Le client valide et paie. Le système enregistre la réservation et affiche son numéro.

Version tabulaire : chaque ligne contient une seule action, soit de l'acteur, soit du système. On voit l'alternance des échanges.

N°Actions de l'acteurActions du système
1Recherche un film
2Affiche les séances disponibles
3Choisit une séance et un nombre de places
4Vérifie les places disponibles, affiche le récapitulatif et le prix
5Valide et paie
6Enregistre la réservation et affiche son numéro

Post-conditions : la réservation est enregistrée ; le nombre de places libres de la séance a diminué.

Alternatif A1 : places insuffisantes

Point d'entrée : étape 4, il reste moins de places que demandé.

N°Actions de l'acteurActions du système
4aIndique le nombre de places restantes
4bAccepte de réduire le nombre de places
4cMet à jour le récapitulatif et le prix

Reprise : étape 5 du nominal.

Exception E1 : séance complète

Point d'entrée : étape 4, il ne reste aucune place.

N°Actions de l'acteurActions du système
4aInforme le client que la séance est complète

Cas terminé : aucune réservation n'est créée.

Diagramme de séquence système (DSS)

Le DSS résume un scénario sous forme de diagramme de séquence. Le système y est une seule ligne de vie, :Système, vue comme une boîte noire : on ne montre que les échanges qui traversent sa frontière, jamais ses objets internes.

  • Les messages de l'acteur vers le système sont les événements système. Ici, le système doit savoir répondre à rechercherSeances(film), choisirSeance(idSeance, nbPlaces) et payer(infosPaiement). En conception, ils deviennent les opérations système.
  • Les retours (pointillés) montrent ce que l'acteur reçoit.
  • On fait un DSS pour le scénario nominal et pour les alternatifs importants. On peut y utiliser loop, opt, alt (voir les fragments).
  • Le DSS fait le lien entre la vue fonctionnelle et la vue dynamique.
Modélisation statique

La classe

Une classe décrit un ensemble d'objets qui ont la même structure (attributs) et le même comportement (opérations). Elle se dessine avec trois compartiments : nom, attributs, opérations.

  1. Nom : au singulier, avec une majuscule. En italique si la classe est abstraite.
  2. Visibilité : + public, - privé, # protégé, ~ paquetage. Syntaxe : visibilité nom : Type = valeurParDéfaut.
  3. Attribut dérivé : précédé de /. Sa valeur se calcule à partir d'autres attributs (l'âge depuis la date de naissance). En code, c'est souvent une méthode getAge() plutôt qu'un champ stocké.
  4. Attribut statique (de classe) : souligné. Une seule valeur partagée par toutes les instances, par exemple un compteur.
  5. Opération : visibilité nom(param : Type, …) : TypeRetour. Une opération statique est aussi soulignée.
  6. Note : commentaire relié par un trait pointillé. Ici, la règle de calcul de l'attribut dérivé.

Le même modèle en PHP :

PHP
class Client
{
    private string $nom;
    private DateTime $dateNaissance;
    protected string $email;
    private static int $nbClients = 0;   // souligné en UML

    public function __construct(string $nom, DateTime $dateNaissance, string $email)
    {
        $this->nom = $nom;
        $this->dateNaissance = $dateNaissance;
        $this->email = $email;
        self::$nbClients++;
    }

    // attribut dérivé /age : calculé, pas stocké
    public function getAge(): int
    {
        return $this->dateNaissance->diff(new DateTime())->y;
    }

    public function reserver(Seance $s, int $nb): Reservation
    {
        return new Reservation($this, $s, $nb);
    }
}

L'association

  1. Nom de l'association, souvent un verbe.
  2. Sens de lecture : petit triangle plein. On lit « un Client effectue des Reservation ». Il n'indique pas la navigabilité.
  3. Multiplicité : combien d'objets de ce côté sont liés à un objet de l'autre côté.
  4. Rôle : nom de l'extrémité. En code, il devient souvent le nom de l'attribut.
Lire les multiplicités

On part d'un objet et on lit le nombre écrit à l'autre bout. Un client effectue 0..* réservations. Une réservation est effectuée par exactement 1 client.

NotationSignification
1exactement un
0..1zéro ou un (facultatif)
* ou 0..*plusieurs, éventuellement aucun
1..*au moins un
2..5entre deux et cinq

Navigabilité : une flèche ouverte au bout d'une association indique que l'on peut aller de A vers B (A connaît B). Un petit x indique un sens non navigable. Sans décoration, la navigabilité n'est pas précisée.

PHP
class Client
{
    /** @var Reservation[] */
    private array $reservations = [];   // rôle « reservations », multiplicité 0..*
}

class Reservation
{
    private Client $titulaire;          // rôle « titulaire », multiplicité 1
}

Les 8 relations à reconnaître

Même trait, autre extrémité : autre signification. Voici les relations du diagramme de classes, avec la notation exacte. Entraînez-vous ensuite dans le quiz « Reconnaître ».

Association

trait plein, sans décoration

Les objets se connaissent durablement (lien structurel).

Exemple Un client assiste à des séances ; une séance accueille des clients.

En code attribut de type objet ou tableau d'objets

Agrégation

losange vide côté tout

Relation tout / partie faible : la partie existe sans le tout et peut être partagée.

Exemple Un morceau peut appartenir à plusieurs playlists et survit à leur suppression.

En code le tout garde des références vers des parties créées ailleurs

Composition

losange plein côté tout

Tout / partie forte : la partie n'appartient qu'à un seul tout et meurt avec lui.

Exemple Supprimer une commande supprime ses lignes de commande.

En code le tout crée lui-même ses parties (new dans le constructeur ou une méthode)

Généralisation (héritage)

trait plein, triangle vide vers le parent

« est une sorte de » : l'enfant hérite des attributs et opérations du parent.

Exemple Un paiement par carte est un paiement.

En code class PaiementCarte extends Paiement

Réalisation (interface)

pointillés, triangle vide vers l'interface

La classe s'engage à fournir les opérations déclarées par l'interface.

Exemple Une réservation implémente l'interface Annulable.

En code class Reservation implements Annulable

Classe d'association

classe reliée en pointillés au milieu de l'association

L'association porte elle-même des données (ou des opérations).

Exemple La note n'appartient ni à l'étudiant ni au cours, mais à l'inscription de l'un à l'autre.

En code une classe Inscription avec une référence vers chaque côté

Association qualifiée

petit rectangle (qualificateur) collé à la classe source

Le qualificateur sert de clé : avec lui, on retrouve un objet précis de l'autre côté.

Exemple Une salle + un numéro de siège désignent au plus un siège.

En code tableau associatif : $sieges[$numero]

Dépendance

pointillés, flèche ouverte vers la classe utilisée

Lien temporaire : une classe en utilise une autre (paramètre, variable locale, appel statique).

Exemple Le générateur de PDF reçoit une réservation en paramètre, sans la garder.

En code function generer(Reservation $r) : sans attribut

Les trois flèches qu'on confond

Triangle vide + trait plein : héritage. Triangle vide + pointillés : réalisation d'interface. Flèche ouverte + pointillés : dépendance. Le triangle pointe toujours vers le plus général (parent ou interface).

Agrégation ou composition ?

Les deux expriment une relation « tout / partie ». La différence porte sur la durée de vie et le partage des parties.

  • La partie existe sans le tout.
  • Elle peut être partagée par plusieurs touts.
  • Supprimer la playlist ne supprime pas les morceaux.
  • La partie appartient à un seul tout à la fois : multiplicité 1 ou 0..1 côté composite.
  • Supprimer la commande supprime ses lignes.
  • Souvent, le tout crée lui-même ses parties.
Le test

« Si je supprime le tout, la partie a-t-elle encore un sens ? » Non → composition. Oui → agrégation (ou simple association).

La norme UML définit précisément la composition. Pour l'agrégation, elle précise que sa sémantique exacte varie selon le domaine et le modélisateur : en cas de doute, une association simple est souvent préférable.

PHP
class Commande
{
    private array $lignes = [];

    public function ajouterLigne(Produit $p, int $qte): void
    {
        $this->lignes[] = new LigneCommande($p, $qte);   // la commande crée ses lignes
    }
}

class Playlist
{
    private array $morceaux = [];

    public function ajouter(Morceau $m): void
    {
        $this->morceaux[] = $m;   // le morceau existait déjà avant
    }
}

Classe abstraite, polymorphisme et redéfinition

  • Classe abstraite : on ne peut pas l'instancier (new Paiement() est interdit). Elle sert de modèle commun. Notation de la norme : nom en italique, et/ou {abstract} sous le nom. Beaucoup de cours et d'outils écrivent aussi «abstract» au-dessus du nom.
  • Opération abstraite : déclarée sans corps, en italique ou suivie de {abstract}. Toute sous-classe concrète doit la définir. Une classe qui a une opération abstraite est forcément abstraite.
  • Redéfinition (overriding) : la sous-classe réécrit une opération héritée, avec la même signature.
  • Polymorphisme : le même appel $p->valider() exécute la version de la classe réelle de l'objet. Le code appelant n'a pas besoin de savoir quel type de paiement il manipule.
RedéfinitionSurcharge
Où ?Dans une sous-classeDans la même classe
SignatureIdentique à l'opération héritéeMême nom, paramètres différents
ExemplePaiementCarte::valider()ajouter(Seance s) et ajouter(Seance s, int nb)
PHPOuiNon : deux méthodes de même nom provoquent une erreur ; on utilise des paramètres optionnels
JavaOui (@Override)Oui
PHP
abstract class Paiement
{
    protected float $montant;

    public function getMontant(): float
    {
        return $this->montant;
    }

    abstract public function valider(): bool;   // pas de corps
}

class PaiementCarte extends Paiement
{
    private string $numeroCarte;

    public function valider(): bool   // redéfinition
    {
        // contrôle de la carte…
        return true;
    }
}

// Polymorphisme : on ne sait pas quel type de paiement on manipule
foreach ($paiements as $p) {
    $p->valider();   // appelle la bonne version
}
Syntaxe PHP. On écrit abstract class Paiement, jamais class abstract Paiement (erreur de syntaxe). Même chose pour les méthodes : abstract public function valider(): bool;, avec un point-virgule et sans accolades.

Interface

Une interface ne déclare que des opérations, sans les implémenter : c'est un contrat. Notation : rectangle avec «interface», et une flèche de réalisation (pointillés, triangle vide) depuis la classe qui l'implémente. En PHP et en Java, une classe n'hérite (extends) que d'une seule classe mais peut implémenter (implements) plusieurs interfaces.

Énumération

Une énumération est un type dont les valeurs possibles sont fixées une fois pour toutes : on restreint les instances à une liste connue.

  1. Le mot-clé «enumeration» (souvent écrit «énumération» dans les cours en français) au-dessus du nom.
  2. Les littéraux : les seules valeurs possibles.
  3. Des opérations éventuelles, comme pour une classe.

En PHP 8.1+, une énumération peut avoir une valeur associée à chaque cas (backed enum), de type int ou string uniquement. Elle peut avoir des méthodes et implémenter des interfaces, mais pas de constructeur ni d'attributs à elle : on calcule les valeurs avec match.

PHP
enum Tarif: string
{
    case PLEIN  = class="s">'P';
    case REDUIT = class="s">'R';
    case ENFANT = class="s">'E';

    public function prix(): float
    {
        return match ($this) {
            Tarif::PLEIN  => 10.50,
            Tarif::REDUIT => 8.00,
            Tarif::ENFANT => 6.00,
        };
    }
}

$t = Tarif::from(class="s">'R');   // Tarif::REDUIT (ValueError si la valeur n'existe pas)
echo $t->value;          // R
echo $t->prix();         // 8

En Java, une énumération peut avoir des attributs et un constructeur (privé) :

Java
public enum Tarif {
    PLEIN(10.50), REDUIT(8.00), ENFANT(6.00);

    private final double prix;

    Tarif(double prix) { this.prix = prix; }

    public double prix() { return prix; }
}
Syntaxe PHP. Si les cas ont une valeur, le type est obligatoire après le nom : enum Tarif: string. Tous les cas doivent alors avoir une valeur, et deux cas ne peuvent pas partager la même.

Diagramme d'objets

Le diagramme d'objets est une photo du système à un instant donné : des objets (instances de classes) et des liens (instances d'associations). Il sert à vérifier un diagramme de classes sur un exemple concret.

  • Nom souligné : nomObjet : Classe. Objet anonyme : :Classe.
  • Attributs avec leur valeur : nom = "Alice". Pas d'opérations.
  • Liens : traits simples, sans multiplicités (un lien relie exactement deux objets).
  • Le diagramme d'objets doit respecter les multiplicités du diagramme de classes : r1 et r2 ont chacune exactement une séance et un client.
Modélisation dynamique

Diagramme de séquence

Il montre comment des objets collaborent dans le temps pour réaliser un scénario. Le temps s'écoule de haut en bas. C'est là qu'on décide quel objet est responsable de quoi.

  1. Acteur : déclenche l'interaction.
  2. Ligne de vie : tête nom : Classe (ou :Classe si l'objet est anonyme) et trait pointillé vertical. UML 1 soulignait ce nom ; UML 2 ne l'impose plus, mais beaucoup de cours le gardent.
  3. Message synchrone : trait plein, pointe pleine. L'émetteur attend la fin de l'opération. On peut récupérer le résultat : seances = chercher(film) (certains cours écrivent :=).
  4. Message de retour : pointillés, pointe ouverte. Facultatif.
  5. Barre d'activation (spécification d'exécution) : période pendant laquelle l'objet exécute une opération.
  6. Message réflexif : l'objet s'appelle lui-même ; une deuxième barre s'empile sur la première.
  7. Création : message en pointillés qui arrive sur la tête du nouvel objet ; sa ligne de vie commence à cette hauteur.
  8. Destruction : croix en bas de la ligne de vie. Plus rien ne se passe après.

Les types de messages

Synchrone

Trait plein, pointe pleine. L'émetteur attend la réponse (appel de méthode classique).

Asynchrone

Trait plein, pointe ouverte. L'émetteur continue sans attendre.

Retour

Pointillés, pointe ouverte. Résultat renvoyé à l'appelant.

Création

Pointillés vers la tête du nouvel objet.

Destruction

Croix sur la ligne de vie détruite.

Réflexif

L'objet s'envoie un message à lui-même.

Trouvé

Part d'un rond noir : l'émetteur est inconnu ou hors du diagramme.

Perdu

Finit sur un rond noir : le destinataire est inconnu ou le message n'arrive pas.

Cadres et fragments combinés

Un diagramme de séquence peut être encadré et découpé en fragments combinés pour exprimer des choix, des boucles ou des renvois vers un autre diagramme.

  1. Cadre sd (sequence diagram) : délimite l'interaction et lui donne un nom.
  2. Porte (gate) : point sur le bord du cadre par où un message entre ou sort. L'émetteur ou le destinataire est hors du diagramme.
  3. Référence ref : renvoie à une autre interaction décrite ailleurs, pour ne pas tout redessiner.
  4. Fragment combiné : rectangle qui regroupe une partie de l'interaction.
  5. Opérateur d'interaction : dans l'onglet en haut à gauche (alt, opt, loop…).
  6. Garde : condition entre crochets. L'opérande ne s'exécute que si elle est vraie. [else] couvre les autres cas.
  7. Séparateur d'opérandes : ligne pointillée entre les branches d'un alt ou d'un par.

Pièges classiques

  1. Flèche «include» dessinée de l'inclus vers la base : c'est l'inverse.
  2. Cas d'utilisation nommé par un nom (« Gestion des comptes », « Base de données ») au lieu d'un verbe.
  3. Trait entre deux acteurs, ou flèches « puis » entre cas : un DUC n'a ni flux ni ordre.
  4. Acteur secondaire dessiné à l'intérieur du système.
  5. Scénario tabulaire avec deux actions sur la même ligne.
  6. Losange dessiné du côté de la partie au lieu du tout.
  7. Composition avec une multiplicité supérieure à 1 côté composite.
  8. Attribut de type classe écrit dans la classe et dessiné en association : choisir l'un des deux.
  9. Triangle d'héritage pointé vers l'enfant ; il pointe toujours vers le parent.
  10. class abstract X en PHP au lieu de abstract class X.
  11. DSS qui montre des objets internes du système : il n'y a qu'une ligne :Système.
  12. Multiplicités affichées sur les liens d'un diagramme d'objets.

Exercice 1

DUC d'une médiathèque

Vue fonctionnelleAnalyse d'énoncé

Une médiathèque veut informatiser ses prêts.

  • Un visiteur non inscrit peut seulement rechercher un document dans le catalogue.
  • Un adhérent peut rechercher un document, emprunter un document et prolonger un emprunt.
  • Pour emprunter ou prolonger, l'adhérent doit s'authentifier avec sa carte.
  • Lors d'un emprunt, s'il a des retards, l'adhérent peut payer une pénalité. Le paiement passe par le système bancaire.
  • Le bibliothécaire ajoute et retire des documents du catalogue.

Dessinez le diagramme de cas d'utilisation.

Méthode
  1. Souligner les acteurs (qui agit ?) et les verbes (que veulent-ils faire ?).
  2. Repérer les acteurs secondaires (systèmes sollicités).
  3. Chercher les mots « doit » (include), « peut / si » (extend), « seulement / aussi » (héritage d'acteurs).
  4. Dessiner le système, les acteurs, les cas, puis les relations.
Correction
  • Adhérent hérite de Visiteur : il peut tout ce que fait le visiteur (rechercher) et plus. On évite ainsi de relier deux fois « Rechercher ».
  • «include» vers S'authentifier depuis Emprunter et Prolonger : « doit », et le comportement est commun aux deux cas.
  • «extend» de Payer une pénalité vers Emprunter : « peut », sous la condition « s'il a des retards ». On peut ajouter le point d'extension retard dans Emprunter.
  • Système bancaire : acteur secondaire (système), hors du système, relié à Payer une pénalité.
  • « Gérer le catalogue » regroupant Ajouter et Retirer est souvent accepté, mais deux cas précis sont plus clairs.
Ce que le correcteur regarde
  • Cas nommés par un verbe à l'infinitif
  • Sens des flèches include/extend
  • Acteurs secondaires hors du système
  • Pas de trait entre acteurs (sauf héritage)
  • Pas de cas « S'authentifier » relié directement à l'acteur sans raison

Exercice 4

Du code PHP au diagramme de classes

Vue statiqueCode → UML

Dessinez le diagramme de classes correspondant à ce code.

PHP
abstract class Document
{
    protected string $titre;
    protected string $cote;
    private static int $nbDocuments = 0;

    abstract public function dureePret(): int;
}

class Livre extends Document
{
    private int $nbPages;
    public function dureePret(): int { return 21; }
}

class DVD extends Document
{
    private int $duree;
    public function dureePret(): int { return 7; }
}

class Adherent
{
    private string $nom;
    /** @var Emprunt[] */
    private array $emprunts = [];

    public function emprunter(Document $d): Emprunt
    {
        $e = new Emprunt($d, new DateTime());
        $this->emprunts[] = $e;
        return $e;
    }
}

class Emprunt
{
    private DateTime $dateDebut;
    private Document $document;

    public function getDateRetour(): DateTime { /* … */ }
}
Méthode
  1. abstract class → nom en italique / {abstract} ; abstract function → opération en italique.
  2. static → souligné ; protected → #.
  3. extends → généralisation (triangle vers le parent).
  4. Attribut dont le type est une autre classe → association navigable, avec le nom de l'attribut comme rôle. Un tableau → multiplicité *.
Correction
  • $emprunts et $document ne sont pas écrits dans les attributs : ils deviennent des associations avec les rôles - emprunts et - document.
  • Le code donne la navigabilité et la multiplicité côté cible (array → 0..*, objet seul → 1). L'autre côté (1 adhérent par emprunt, * emprunts par document) vient du sens métier, pas du code.
  • Comme l'adhérent crée ses emprunts, une composition Adherent ◆ Emprunt se défend aussi.
  • DateTime se note simplement Date.
Ce que le correcteur regarde
  • Italique / {abstract} sur la classe et l'opération
  • Attribut statique souligné
  • Héritage vers Document
  • Associations à la place des attributs objets
  • Multiplicités et rôles
Exercice 5

Du diagramme de classes au code PHP

Vue statiqueUML → code

Écrivez les trois classes en PHP, avec les constructeurs et le corps de total() et sousTotal().

Méthode
  1. Chaque attribut → propriété typée avec la bonne visibilité.
  2. Association navigable de multiplicité 1 → propriété objet ; * ou 1..* → tableau.
  3. Composition → le tout crée ses parties (new dans ses méthodes).
  4. Le calcul suit les flèches : Commande → LigneCommande → Produit.
Correction
PHP
class Produit
{
    private string $libelle;
    private float $prix;

    public function __construct(string $libelle, float $prix)
    {
        $this->libelle = $libelle;
        $this->prix = $prix;
    }

    public function getPrix(): float { return $this->prix; }
}

class LigneCommande
{
    private int $quantite;
    private Produit $produit;                 // rôle produit, multiplicité 1

    public function __construct(Produit $p, int $qte)
    {
        $this->produit = $p;
        $this->quantite = $qte;
    }

    public function sousTotal(): float
    {
        return $this->produit->getPrix() * $this->quantite;
    }
}

class Commande
{
    private int $numero;
    private DateTime $date;
    /** @var LigneCommande[] */
    private array $lignes = [];               // composition 1..*

    public function __construct(int $numero)
    {
        $this->numero = $numero;
        $this->date = new DateTime();
    }

    public function ajouterLigne(Produit $p, int $qte): void
    {
        $this->lignes[] = new LigneCommande($p, $qte);   // la commande crée ses lignes
    }

    public function total(): float
    {
        $total = 0;
        foreach ($this->lignes as $ligne) {
            $total += $ligne->sousTotal();
        }
        return $total;
    }
}

LigneCommande ne connaît pas sa Commande : l'association n'est navigable que de Commande vers LigneCommande. Pour garantir 1..*, on pourrait exiger une première ligne dans le constructeur de Commande.

Ce que le correcteur regarde
  • Visibilités respectées
  • Tableau pour les multiplicités multiples
  • new LigneCommande dans Commande (composition)
  • Navigabilité respectée (pas d'attribut commande dans LigneCommande)

Exercice 7

Du diagramme de séquence au code

Vue dynamiqueVue statiqueUML → code

Écrivez la méthode valider() de la classe Panier, puis dites ce que ce diagramme impose au diagramme de classes.

Méthode
  1. Les messages qui partent de p sont les instructions de la méthode, dans l'ordre vertical.
  2. alt → if / else ; un create → new ; un message réflexif → $this->….

Correction
PHP
class Panier
{
    private Stock $stock;
    private array $articles = [];

    public function valider(): ?Commande
    {
        $dispo = $this->stock->verifier($this->articles);
        if ($dispo) {
            $c = new Commande($this->articles);
            $this->vider();
            return $c;

        return null;

Exercice 9

DUC : trouvez les 5 erreurs

Vue fonctionnelleVérification

Listez les cinq erreurs de notation ou de modélisation.

Méthode

Vérifiez un par un : le sens des flèches, les noms des cas, ce qui relie les acteurs, la présence d'un ordre, et la position des acteurs.
