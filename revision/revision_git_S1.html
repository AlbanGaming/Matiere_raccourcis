Les bases

Pourquoi Git ?

Git est un gestionnaire de versions : il enregistre l'historique d'un projet sous forme d'instantanés (les commits). On peut revenir à n'importe quelle version, voir qui a changé quoi, et travailler à plusieurs sur le même code sans s'écraser.

Git est distribué : chaque développeur a une copie complète du dépôt et de son historique sur sa machine. On travaille hors ligne, et on synchronise avec un dépôt distant quand on veut.

Git ≠ GitHub. Git est le logiciel, installé sur ta machine. GitHub et GitLab sont des sites qui hébergent des dépôts Git et ajoutent des outils (pull requests, issues, intégration continue).

Installer et configurer

Une fois Git installé, on se présente une fois pour toutes : ce nom et cet e-mail sont écrits dans chaque commit.

git --version
git config --global user.name "Prénom Nom"
git config --global user.email "prenom.nom@exemple.fr"
git config --global init.defaultBranch main   # branche par défaut : main
git config --global core.editor "code --wait"  # éditeur pour les messages
git config --list                              # vérifier
--global s'applique à tous tes dépôts (fichier ~/.gitconfig). Sans l'option, le réglage ne vaut que pour le dépôt courant.

Créer ou récupérer un dépôt

Partir de zéro

cd mon-projet
git init

Crée un dossier caché .git : c'est lui, le dépôt. Le supprimer efface tout l'historique.

Copier un dépôt existant

git clone https://github.com/user/projet.git

Télécharge le projet et tout son historique, et mémorise l'adresse sous le nom origin.

Les trois zones

C'est LE schéma à comprendre. Un changement passe par trois endroits avant d'être enregistré, puis un quatrième pour être partagé.

git add index.html          # un fichier vers l'index
git add .                   # tous les changements du dossier
git commit -m "feat: ajoute la page d'accueil"
git push                    # envoie les commits sur le distant
Pourquoi l'index ? Pour choisir. Tu as modifié 5 fichiers mais seulement 2 concernent la correction d'un bug : tu n'ajoutes que ces 2-là, tu commits, puis tu fais un 2e commit pour le reste. Un commit = une modification cohérente.

Le cycle de vie d'un fichier

$ git status
On branch main
Changes to be committed:        ← dans l'index, partira au prochain commit
        modified:   style.css
Changes not staged for commit:  ← modifié mais pas encore ajouté
        modified:   index.html
Untracked files:                ← jamais suivi par Git
        notes.txt

Le commit

Un commit est un instantané complet du projet à un moment donné, avec un auteur, une date, un message et un lien vers son ou ses parents. Il est identifié par un hash (SHA-1) : a3f9c2e…, dont on utilise souvent les 7 premiers caractères.

Commits petits et fréquents. Un commit doit pouvoir se résumer en une phrase. « Plein de trucs » n'est pas un message de commit (voir les conventions).

Ignorer des fichiers : .gitignore

Certains fichiers ne doivent jamais être versionnés : dépendances téléchargées, fichiers compilés, mots de passe, réglages de ton IDE.

# .gitignore
node_modules/        # un dossier entier
vendor/
*.log                # tous les fichiers .log
.env                 # secrets !
.env.local
.idea/
.vscode/
build/
!build/README.md     # exception : celui-là est suivi
Trop tard ? Un fichier déjà commité reste suivi même s'il est ajouté au .gitignore. Il faut d'abord le retirer de l'index : git rm --cached .env, puis commiter. Et si c'était un mot de passe, change-le : il est dans l'historique.
Branches

Une branche, c'est un pointeur

Une branche n'est pas une copie du projet : c'est une simple étiquette mobile qui pointe vers un commit. Quand tu commits, l'étiquette de la branche courante avance toute seule. HEAD est l'étiquette spéciale qui indique la branche sur laquelle tu es.

On crée une branche pour chaque fonctionnalité ou correction : on travaille dessus sans casser main, puis on la fusionne quand c'est prêt.

Créer et changer de branche

git branch                       # liste (* = branche courante)
git branch feature/connexion     # crée (sans y aller)
git switch feature/connexion     # y aller  (ancien : git checkout)
git switch -c feature/connexion  # créer ET y aller (ancien : git checkout -b)
git branch -d feature/connexion  # supprimer (si fusionnée)
Avant de changer de branche, commite ou mets de côté (stash) tes modifications : sinon Git refuse, ou les emporte avec toi.

Fusionner (merge)

On se place sur la branche qui reçoit les changements, puis on fusionne l'autre :

git switch main
git merge feature/connexion

Cas 1 : avance rapide (fast-forward)

main n'a pas bougé depuis la création de la branche : Git avance simplement l'étiquette. Aucun nouveau commit.

Cas 2 : commit de fusion (merge à trois points)

Les deux branches ont avancé : Git crée un commit de fusion (ici M) qui a deux parents.

Résoudre un conflit

Si les deux branches ont modifié les mêmes lignes d'un fichier, Git ne peut pas choisir : il s'arrête et marque le conflit dans le fichier.

<<<<<<< HEAD
<h1>Bienvenue sur le site</h1>
=======
<h1>Bonjour et bienvenue</h1>
>>>>>>> feature/accueil

Au-dessus de ======= : ta version (HEAD). En dessous : celle de la branche fusionnée.

  1. git status liste les fichiers en conflit (« both modified »).
  2. Ouvre chaque fichier, garde la bonne version (ou un mélange) et supprime les marqueurs.
  3. git add fichier pour signaler que le conflit est résolu.
  4. git commit pour terminer la fusion (ou git rebase --continue pendant un rebase).
Panique ? git merge --abort annule la fusion en cours et revient à l'état d'avant.
Travailler à plusieurs

Dépôts distants

git remote -v                                  # liste des distants
git remote add origin https://github.com/user/projet.git
git push -u origin main     # 1er envoi : -u lie main à origin/main
git push                    # ensuite, simplement
git fetch                   # récupère sans toucher à tes fichiers
git pull                    # fetch + merge (ou rebase avec --rebase)
« rejected (fetch first) » au moment du push : quelqu'un a poussé avant toi. Fais git pull, règle les éventuels conflits, puis git push. Ne force jamais avec --force sur une branche partagée.

Le rebase

Le rebase est l'autre façon d'intégrer des changements. Au lieu de créer un commit de fusion, il rejoue tes commits un par un au-dessus de l'autre branche, comme si tu avais commencé ton travail plus tard.

git switch feature
git rebase main

Ensuite, sur main, un git merge feature sera une simple avance rapide : historique parfaitement linéaire.

merge

  • Ne réécrit rien, sûr sur une branche partagée
  • Garde la trace exacte de ce qui s'est passé
  • Historique avec des « bulles » de fusion

rebase

  • Historique linéaire, plus lisible
  • Réécrit les commits (nouveaux hashs)
  • Conflits à régler commit par commit (git rebase --continue)
Règle d'or : ne rebase jamais des commits déjà poussés et utilisés par d'autres. Tu réécrirais une histoire que tes coéquipiers ont déjà : leurs dépôts ne colleraient plus au tien. Rebase seulement ton travail local, avant de le partager.

Pratique : pull --rebase

git pull --rebase récupère le travail des autres puis replace tes commits locaux par-dessus, au lieu de créer un commit de fusion inutile à chaque pull.

Le rebase interactif

git rebase -i HEAD~3 ouvre la liste des 3 derniers commits : on peut les réordonner, renommer (reword), fusionner (squash) ou supprimer (drop). Pratique pour nettoyer son travail avant une pull request, toujours sur des commits pas encore partagés.

pick   2f0c9aa feat: formulaire de connexion
squash 71be3d2 wip
squash 9d1e4b7 oubli d'un fichier
# → un seul commit propre « feat: formulaire de connexion »

Le workflow GitHub / GitLab

  1. git switch main puis git pull : partir d'une base à jour.
  2. git switch -c feature/42-connexion : une branche pour la tâche.
  3. Commits réguliers, avec des messages clairs.
  4. git push -u origin feature/42-connexion
  5. Ouvrir une pull request / merge request, faire relire, corriger.
  6. Fusion dans main, puis suppression de la branche.
Fork : copie d'un dépôt sous ton propre compte, quand tu n'as pas le droit d'écrire sur l'original (projet open source). Tu proposes ensuite tes changements par pull request.
Annuler

Annuler sans paniquer

Je veux…Commande
Annuler mes modifs d'un fichier (pas encore ajouté)git restore fichier
Retirer un fichier de l'index (garder les modifs)git restore --staged fichier
Corriger le message ou ajouter un oubli au dernier commitgit add oubli.txt puis git commit --amend
Annuler un commit déjà pousségit revert a3f9c2e
Défaire les derniers commits locauxgit reset (voir ci-dessous)
Annuler une fusion ou un rebase en coursgit merge --abort · git rebase --abort
Retrouver un commit « perdu »git reflog (journal de tous les déplacements de HEAD)
Attention : git restore fichier et git reset --hard effacent des modifications non commitées. Celles-là, Git ne peut pas les récupérer.

reset, revert, restore

revert : annuler en ajoutant

git revert crée un nouveau commit qui fait l'inverse d'un ancien. L'historique n'est pas réécrit : c'est la bonne méthode sur une branche partagée.

reset : reculer la branche

git reset HEAD~1 fait reculer l'étiquette de la branche d'un commit. Les trois options disent ce qu'on garde :

OptionIndexRépertoire de travailUsage
--softgardé (modifs indexées)gardérefaire le commit autrement
--mixed (défaut)vidégardére-choisir ce qu'on indexe
--hardvidéeffacétout jeter (dangereux)
Comme le rebase : reset réécrit l'historique. Seulement sur des commits pas encore poussés.

Mettre de côté : stash

Tu dois changer de branche en urgence mais ton travail n'est pas prêt à être commité :

git stash            # range les modifs en cours, le dossier redevient propre
git switch main      # … correction urgente …
git switch feature
git stash pop        # ressort les modifs
git stash list       # voir ce qui est rangé
Conventions de nommage

Messages de commit

Un bon message permet de comprendre l'historique sans ouvrir le code. La convention la plus répandue est Conventional Commits :

type(portée optionnelle): description courte à l'impératif

Corps facultatif : le pourquoi, pas le comment.

Refs #42
TypeQuand l'utiliserExemple
featnouvelle fonctionnalitéfeat: ajoute la connexion par e-mail
fixcorrection de bugfix(panier): corrige le total avec remise
docsdocumentation uniquementdocs: complète le README
stylemise en forme du code, sans changer son comportementstyle: indentation du contrôleur
refactorrestructuration sans nouvelle fonction ni correctionrefactor: extrait la validation dans un service
testajout ou correction de teststest: couvre le calcul de TVA
choremaintenance (dépendances, config, build)chore: met à jour composer.lock
perfamélioration de performanceperf: met en cache la liste des produits

✅ À faire

  • Verbe à l'impératif présent (en français : « ajoute », « corrige »)
  • Première ligne courte : 50 caractères environ, 72 maximum
  • Pas de point final sur la première ligne
  • Une ligne vide avant le corps
  • Une seule modification logique par commit

❌ À éviter

  • update, modif, fix tout seul
  • wip, test, aaa, ça marche enfin
  • Un message qui décrit le code au lieu du but
  • Mélanger français et anglais dans un même projet
Choisir une langue et s'y tenir : l'anglais est la norme en entreprise et en open source, le français est accepté en projet scolaire. L'important est que toute l'équipe fasse pareil.

Noms de branches

Un nom de branche dit ce qu'on fait et pour quoi. Format courant : type/numero-description-courte, en minuscules et avec des tirets (kebab-case).

PréfixeUsageExemple
mainbranche principale, toujours stablemain (anciennement master)
developintégration en cours (Git Flow)develop
feature/ ou feat/nouvelle fonctionnalitéfeature/42-connexion-google
fix/ ou bugfix/correction de bugfix/57-total-panier
hotfix/correction urgente en productionhotfix/faille-xss-recherche
release/préparation d'une versionrelease/1.2.0

alban
test2
Ma Branche

Pourquoi le numéro ? Il relie la branche à l'issue ou au ticket (GitHub, GitLab, Jira). Sur GitHub, écrire Closes #12 dans la pull request ferme l'issue automatiquement à la fusion.

Tags, dépôts, fichiers

Tags de version : SemVer

Un tag marque une version précise. On suit le versionnement sémantique vMAJEUR.MINEUR.CORRECTIF :

On incrémente…QuandExemple
MAJEURchangement incompatible avec l'existantv1.4.2 → v2.0.0
MINEURnouvelle fonctionnalité compatiblev1.4.2 → v1.5.0
CORRECTIFcorrection de bug compatiblev1.4.2 → v1.4.3
git tag -a v1.0.0 -m "Première version publique"
git push origin v1.0.0     # les tags ne partent pas avec un push simple

Noms de dépôts et de fichiers

  • Dépôt : en minuscules, mots séparés par des tirets : gestion-stock, portfolio-web (pas Projet Final V2)
  • Pas d'espaces ni d'accents dans les noms de fichiers versionnés : page-contact.html
  • Toujours un README.md (présentation, installation, utilisation) et un .gitignore
